\label{chapter:design}

\section{From Domain Analysis to a Feature Model}

The review in Chapter~\ref{chapter:related_work} shows that a monitoring
solution is not defined by one checker. It combines choices about observable
elements, observation and checking placement, monitoring mode, operation, and
implementation. A feature model keeps these choices explicit and separates the
description of the domain from the configuration chosen for one prototype.

The domain model in Figure~\ref{fig:feature-model-domain} was derived by
identifying recurring capabilities in the reviewed literature, merging
synonymous ones, and recording dependencies between branches as cross-tree
constraints. It uses the FODA notation introduced in
Section~\ref{sec:feature-models} and captures the design space rather than one
tool. Deployment parameters such as host addresses, ROS names, and class paths
are not features; they belong to the deployment specification.

\subsection{Feature Groups}

\begin{description}
  \item[Observable elements.] Application-level observation means typed data
  exposed by the ROS~2 graph: topics, service events, and action feedback or
  status. The domain additionally offers parameters, node and lifecycle
  states, and middleware QoS events such as missed deadlines, liveliness
  changes, and incompatible-QoS notifications on the publisher and subscriber
  sides.

  \item[Observation mechanism.] The same element can often be observed in
  several ways: through a monitor node that uses native ROS~2 interfaces,
  through instrumentation or decorators inside the application, through a
  network tap, through execution tracing such as LTTng, or through
  vendor-specific DDS monitoring tools.

  \item[Monitoring architecture.] Collection and checking may be integrated or
  split; a transport is required whenever data crosses a runtime boundary,
  which the model records as a mandatory child of the split feature.

  \item[Monitoring mode.] Passive and active behaviour form an or group and
  may coexist. A checker is applicable in both cases: a passive
  solution reports its verdict, while an active solution can additionally use
  it for feedback.

  \item[System configuration.] Monitoring may be online, offline, or both; it
  may observe one or several robots; and it may use one or several hosts.

  \item[Implementation paradigm.] A solution can be configured, generated, and
  extended through plug-ins. These mechanisms are complementary rather than
  exclusive.
\end{description}

\section{Selected Requirements}

The domain analysis and selected feature configuration yield the following
requirements:

\begin{description}
  \item[R1: Heterogeneous observation.] Topic messages, service request and
  response events, and action feedback and status must enter one processing
  model without erasing their differences.

  \item[R2: Common observation format.] Every collected observation must be
  converted to a common format that preserves source, phase, time, payload,
  session, and record identity.

  \item[R3: Configurable processing and routing.] Field selection, rate
  limiting, change filtering, outputs, and checking chains must be selected
  without changing collector code.

  \item[R4: Property-formalism independence.] Users must be able to plug in
  their own conversion to a checker event format and their own property
  formalism or checking service.

  \item[R5: Deployment variation.] The same monitoring responsibilities must
  support integrated and split deployment, with explicit transport
  configuration.

  \item[R6: Traceable evidence.] A verdict must be able to identify the
  observation records that contributed to it.

  \item[R7: Extensibility.] It must be possible to add new sources,
  transformers, transports, converters, verdict services, and exporters
  behind stable interfaces.
\end{description}

  extension only.}
  \label{fig:reference-architecture}

\begin{enumerate}
  \item A \emph{collector} observes one typed ROS~2 source. A
  \emph{transport source} performs the corresponding runtime for records arriving
  from a file or MQTT.

  \item The collector creates a \emph{common data record}. This is the first
  format shared by all later components.

  \item Zero or more \emph{transformers} select fields, limit rate, flatten
  structure, or suppress unchanged values.

  \item A \emph{dispatcher} routes a record to one or more data exporters and
  checking chains. Data exporters retain JSONL evidence or send records over a
  configured transport.

  \item A \emph{converter plug-in} converts a common data record into the input
  expected by a checker. A domain-specific language (DSL) is a language tailored
  to one problem domain, such as temporal properties or event-state patterns.
  The architecture calls the converter output a DSL record because every
  property formalism may require a different shape.

  \item A \emph{verdict-service plug-in} evaluates the property through a local
  implementation or an external checking engine.

  \item A \emph{verdict exporter} writes or publishes the result. The verdict
  retains the contributing record identifiers.
\end{enumerate}

A plug-in is a user-developed Python class loaded by its module and class name.
A converter implements the stable conversion interface; a verdict service
implements the stable evaluation interface. To add a DSL, a developer defines
the DSL-record fields, implements these two classes, tests them against sample
records, and selects their class paths and settings in the deployment
specification. ROS~2 collection, transport, and evidence handling are reused.

The architecture also shows an optional feedback adapter. It could translate a
verdict into a ROS~2 command, service request, or other intervention. The
prototype neither implements this adapter nor claims active enforcement.

\section{Common Data Record}\label{sec:common-record}

The common data record separates observation from checker representation.
Table~\ref{tab:data-record-fields} defines its principal fields. The full schema
and an example appear in Appendix~\ref{app:data-record}.

\begin{table}[htbp]
\centering
\caption{Principal fields of the common data record.}
\label{tab:data-record-fields}
\begin{tabular}{p{.24\textwidth}p{.65\textwidth}}
\toprule
\textbf{Field} & \textbf{Meaning}\\
\midrule
\texttt{session\_id}, \texttt{record\_id} & Execution identity and stable
observation identity.\\
\texttt{source\_type}, \texttt{source\_name} & Topic, service, or action and
its ROS~2 name.\\
\texttt{source\_node}, \texttt{msg\_type} & Discovered producer/server and
ROS~2 interface type.\\
\texttt{phase} & Empty for a normal topic; request/response or feedback/status
for heterogeneous interactions.\\
\texttt{timestamp}, \texttt{ros\_timestamp} & Monitor receive time and an
optional timestamp from the ROS message.\\
\texttt{data} & Recursively converted observation payload.\\
\texttt{metadata} & Sequence number, QoS information, and applied
transformers.\\
\bottomrule
\end{tabular}
\end{table}

ROS~2 messages can contain primitive values, nested messages, arrays,
sequences, and time values. The collector recursively converts them to a
JSON-compatible tree: Boolean, numeric, and string fields become JSON scalars;
nested messages become objects; arrays and sequences become arrays; and ROS
time uses \texttt{sec} and \texttt{nanosec} fields. The surrounding record
stores type and source identity, so nesting is preserved without requiring a
checker to import the original ROS~2 class. Arbitrary Python objects are not
part of the interchange contract.

For example, a \texttt{geometry\_msgs/msg/Twist} message is represented as
nested \texttt{linear} and \texttt{angular} objects. A speed converter may
retain only \texttt{linear.x}, while the original JSONL record can still be
kept as evidence. Service-event metadata also carries the client identifier and
sequence number needed to pair requests and responses.

\section{Representative Deployment Views}\label{sec:deployment-views}

Figure~\ref{fig:deployment-views} shows the two deployment forms defined in
Section~\ref{sec:deployment-terminology}. In the notation of the figure, outer
boxes are hosts and inner boxes are executable runtimes; arrows carry common
data records. A \emph{ROS~2-facing runtime} is a process with ROS~2 libraries
and graph access; it is not necessarily running on the robot itself. In terms
of the monitoring organizations of
Section~\ref{sec:monitoring-organisations}, the integrated form realizes the
traditional organization, and the split form realizes an orchestrated
organization with one central verifier.

\begin{figure}[htbp]
  \centering
  \resizebox{\textwidth}{!}{\input{figures/deployment_views}}
  \caption{Integrated and split deployments. These are representative
  configurations, not the only placements allowed by the architecture.}
  \label{fig:deployment-views}
\end{figure}

The integrated form minimizes transport boundaries. The split form isolates
the checker from ROS~2 dependencies and permits a different host or operating
system. More configurations can be formed by adding monitor runtimes, verifier
runtimes, and explicit links in the deployment specification. Such a
configuration still requires network addresses, credentials, topics or file
paths, and component placement; the feature model alone cannot supply them.

\section{Chapter Summary}

The feature model distinguishes domain choices from deployment parameters. The
reference architecture realizes the selected path as a sequence of collectors,
common records, transformers, dispatchers, converter plug-ins, verdict-service
plug-ins, and exporters. It supports integrated and split placements while
keeping active feedback outside the current prototype. The next chapter
explains how this design is implemented and generated.
