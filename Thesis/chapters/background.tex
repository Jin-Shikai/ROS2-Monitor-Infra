\chapter{Background}\label{chapter:background}

This chapter introduces the concepts that the rest of the thesis builds on:
ROS~2 and its communication mechanisms, runtime monitoring and its
terminology, the ways in which ROS~2 applications can be observed, feature
models as a notation for variability, and the organizations, deployment
terms, and transports of distributed monitoring.

\section{ROS 2 Applications and Communication}\label{sec:ros2-communication}

\subsection{Nodes and the ROS Graph}

ROS~2 is a middleware and software platform for building robotic applications.
It provides communication and discovery mechanisms among the components of a
robotic system, and many reusable packages that help components work together
in different applications~\cite{macenski2022ros2}.

A ROS~2 application is usually divided into \emph{nodes}. Each node has a
focused task. For example, one node may publish camera data, another node may
plan a route, and another node may control the motors. The active nodes and
their communication links form the \emph{ROS graph}. Nodes can run on the same
computer or on different computers.

ROS~2 communication uses defined types. A type describes the fields of the
data that nodes exchange, and client libraries such as \texttt{rclcpp} and
\texttt{rclpy} provide the matching C++ and Python APIs. Nodes communicate
through three main mechanisms: topics, services, and
actions~\cite{ros2interfaces,macenski2022ros2}. The following subsections
explain each mechanism.

\subsection{Topics}

A topic is a named publish--subscribe channel. Publishers send messages without
addressing individual receivers, and any number of subscribers may receive
them. Topics are suited to streams such as sensor measurements, robot pose, or
velocity commands. Delivery behaviour depends on compatible Quality of Service
(QoS) policies such as reliability, durability, history, and
depth~\cite{ros2topics,ros2qos}.

  \caption{Topic communication. Author's illustration based on the ROS~2
  topic model~\cite{ros2topics}.}
  \label{fig:topic-communication}
\end{figure}

\subsection{Services}\label{sec:ros2-services}

A service represents a request--response interaction. A client sends a typed
request and a server returns a typed response. The exchange is one-to-one: the
request travels from one client to the server, and the response travels back
to that client only. ROS~2 service introspection can publish request and
response events on a hidden \texttt{/<service>/\_service\_event} topic when
introspection is enabled by the client or
server~\cite{ros2serviceintrospection}. This event stream lets a monitor
observe a service without becoming the client or server;
Section~\ref{sec:observing-services} explains this mechanism in detail.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=.72\textwidth]{diagrams/Services.png}
  \caption{Service communication. Author's illustration based on the ROS~2
  service model~\cite{ros2interfaces}.}
  \label{fig:service-communication}
\end{figure}

\subsection{Actions}

An action represents a long-running goal. It combines service interactions for
goal management with hidden topics for feedback and status. A client can send a
goal, receive progress feedback, request cancellation, and obtain a final
result~\cite{ros2actions}. Monitoring feedback and status reveals progress and
terminal goal states. A complete action trace additionally requires the hidden
goal, cancellation, and result service events.

\end{figure}

\subsection{Discovery, Middleware, and Quality of Service}
\label{sec:discovery-qos}

ROS~2 commonly uses Data Distribution Service (DDS) middleware for
communication. DDS provides distributed discovery, so ROS~2 does not need the
central master used in ROS~1~\cite{macenski2022ros2}. Nodes can discover the
names and types of visible topics and services at runtime. Discovery takes
time, however, and the ROS graph can change while the application is running,
so the set of visible names and types is not a fixed snapshot.

ROS~2 also provides QoS settings that control reliability, stored history,
durability, deadlines, and other communication behaviour~\cite{ros2qos}. Two
endpoints can only communicate when their QoS settings are compatible. Both
properties matter for monitoring: a monitor that joins the graph must wait for
discovery, and its subscriptions must request QoS settings compatible with the
observed publishers.

\section{Runtime Monitoring Concepts}\label{sec:runtime-monitoring}

Runtime monitoring refers to observing a system while it is running. It can
support several purposes, including operational diagnosis, error detection,
security monitoring, and requirements checking~\cite{rabiser2019domain}.
Runtime verification is a closely related technique in which an observed
execution is checked against a specification~\cite{leucker2009brief}. It can
report whether the observed behaviour satisfies or violates a property, but it
does not establish correctness for all possible executions. In this thesis,
runtime monitoring is used as the broader term for observing and processing
runtime data, while runtime verification denotes the property-checking task
that such monitoring can support.

This thesis uses the following terms consistently:

\begin{description}
  \item[System under monitoring.] The running ROS~2 application whose
  behaviour is observed.

  \item[Observation.] A value or event obtained from the system under
  monitoring, such as a topic message, service response, or action status.

  \item[Trace.] A sequence of observations, either processed live or retained
  for later checking.

  \item[Property.] A condition expected of the observed behaviour. A property
  can be expressed as a temporal-logic formula, a rule, a state machine, or
  another formalism.

  \item[Monitor.] The component that obtains and prepares observations.

  \item[Checker.] The component that evaluates a property using prepared
  observations.

  \item[Verdict.] A checking result, normally indicating satisfaction,
  violation, or an inconclusive state.
\end{description}

Figure~\ref{fig:monitoring-terms} shows how these terms relate. The monitor
captures observations from the system under monitoring. Based on a property,
the checking component evaluates the observed behaviour and reports a verdict
to a user or to another component.

\subsection{Online and Offline Monitoring}

Online monitoring processes observations during an execution. It can report
problems quickly and is suitable for timely warnings and supervision. Offline
monitoring checks recorded observations later. It cannot react immediately, but the same data can be
replayed many times and checked with tools that are easier to run outside the
robot application. The same monitoring infrastructure may support both by
routing a common record either to a live checker or to persistent storage.

\subsection{Passive and Active Monitoring}

A passive monitor observes, checks, and reports without changing the behaviour
of the system under monitoring. An active monitor can additionally block,
replace, or trigger behaviour, for example by filtering a message or starting
a recovery action. Passive and active behaviour are not mutually exclusive at
architecture level: the same solution may record all observations and
intervene only after selected verdicts. A checker may be used in either mode.
The prototype in this thesis implements only passive monitoring.

\subsection{Centralized and Distributed Checking}

Collection and checking may run in one process, on one host in separate
processes, or on different hosts. Keeping the checking state in one place
simplifies the design, although the central component can become a bottleneck
or a single point of failure. Distributing observation or checking work places
monitoring logic closer to the data source or closer to a verifier, but it
introduces questions about message ordering, clocks, network boundaries, and
failures~\cite{francalanza2018distributed}.
Section~\ref{sec:monitoring-organisations} describes the main ways in which
such monitors can be organized. The split deployment in this thesis separates
collection from checking, but checking remains logically centralized in a
verifier.

\subsection{Property Specification Formalisms}

Properties can be written in several forms. Temporal logics express ordering,
deadlines, and time-bounded relationships. Rules express conditions and
event--condition--action behaviour. Grammars describe valid event sequences,
while finite-state machines describe allowed states and transitions. Stream
languages compute derived values and verdicts from timestamped input. Each
checker consequently expects its own input representation. This thesis remains
neutral about the formalism and adapts common observations through converter
and verdict-service plug-ins~\cite{leucker2009brief}.

\section{Observing ROS 2 Applications}\label{sec:observing-ros2}

A monitor for a ROS~2 application first has to obtain observations. The three
communication mechanisms from Section~\ref{sec:ros2-communication} can each be
observed, but not in the same way. This section explains the observation mechanism for each of them,
the runtime that types and discovery play for a monitor, and the alternative
mechanisms that operate below the ROS~2 API.

\subsection{Observing Topics}

A monitor can observe a topic by creating an extra subscription, as any other
node would. This is a simple and passive method because the original
communication path does not need to change. Common ROS~2 tools such as
\texttt{ros2 topic echo} and \texttt{ros2 bag record} work in this way.

Topic observation still requires several choices. Some topics publish large
messages or publish at a high rate, while a monitor may only need a few fields
or a subset of the messages. The monitoring subscription must also use a QoS
setting that is compatible with the publisher; otherwise it may receive no
messages or lose data under high load. Finally, messages from different
publishers may arrive in a different order from the order in which they were
sent.

\subsection{Observing Services}\label{sec:observing-services}

Services cannot be observed in the same way as topics. As explained in
Section~\ref{sec:ros2-services}, a service call is a one-to-one exchange. A
third node that wants to watch the service cannot ``listen in'' on this
exchange. If it creates its own client for the same service, it can only make
its own calls; it never sees the requests and responses of other clients.

ROS~2 solves this with \emph{service introspection}. When introspection is
enabled on the client or the server, that node publishes an event message on
an additional \emph{service event topic} for every step of a call. Each event
carries metadata (such as the event type, a client identifier, a sequence
number, and a timestamp) and can also carry the request or response
payload~\cite{ros2serviceintrospection}. Because the events are published on a
normal topic, a monitor can observe them with a plain subscription, as shown
in Figure~\ref{fig:service-introspection}.

This mechanism keeps the observation passive, but it has two consequences for
a monitor. First, introspection must be enabled by the application; without
it, the event topic carries no data. Second, a request and its response arrive
as separate event messages, so the monitor must use the event metadata, such
as the client identifier and sequence number, to connect a response to the
correct request.

\subsection{Observing Actions}

Actions combine the previous two cases, because they are built from hidden
topics and services. The feedback and status streams are topics, so a monitor
can subscribe to them directly. The goal, result, and cancellation exchanges
are services, so observing them requires service introspection on the action
server or client.

\subsection{Types and Discovery for Monitors}

A monitor needs the correct type before it can read and understand captured data.
Discovery can help a monitor find the type of a topic or service
automatically, but as explained in Section~\ref{sec:discovery-qos}, discovery
takes time and the graph can change at runtime, so a monitor should not assume
that every source is already visible at startup.

The ROS graph also shapes what monitoring looks like in ROS~2. A monitoring
node can often join the graph without changing the original application, which
makes passive observation natural. At the same time, the behaviour of the full
robot is spread over many nodes, so a monitor must select useful interfaces
and keep enough context to connect related events.

\subsection{Alternative Observation Mechanisms}
\label{sec:observation-mechanisms}

The mechanisms above use native ROS~2 interfaces: normal subscriptions,
service-introspection event topics, and hidden action topics. They retain ROS
names and types and are well suited to application-level properties, but they
depend on DDS discovery and compatible QoS. Three further categories of
observation mechanisms exist:

\begin{description}
  \item[Application instrumentation.] Monitoring calls or wrappers are added to
  application code. This can expose domain events that ROS communication does
  not reveal, at the cost of changing the application.

  \item[Network observation.] Packet capture or network probes observe traffic
  without normal ROS subscriptions. They can support security analysis but may
  have to reconstruct ROS meaning from middleware or packet data.

  \item[Tracing.] ROS~2, middleware, or operating-system tracepoints observe
  callbacks, scheduling, middleware operations, and execution timing. This
  provides lower-level evidence than typed application messages.
\end{description}

The prototype uses the native ROS~2 interfaces; approaches based on the other
categories are reviewed in Chapter~\ref{chapter:related_work}.

\section{Common Monitoring Tasks and Data Forms}

The monitoring-domain analysis by Rabiser et al.\ identifies recurring tasks
such as definition, instrumentation, collection, processing, routing, checking,
and persistency~\cite{rabiser2019domain}. For this thesis they are organized as
six operational tasks:

\begin{enumerate}
  \item collect observations;
  \item convert raw observations to a common representation;
  \item transform or reduce the data;
  \item route or transport it;
  \item adapt it to a checker and evaluate properties; and
  \item export the verdict or retain evidence.
\end{enumerate}

Each task has its own concerns. Collection uses one of the observation
mechanisms from Section~\ref{sec:observing-ros2}. Processing selects fields,
adds context, and reduces data volume. Routing sends the same data to several
destinations without changing the collectors. Checking needs a
checker-specific input format: a threshold checker may need one number, while
a temporal-logic checker needs timestamped values. Finally, a verdict is only
useful when it reaches the right user or component.

The data changes form along this path. A \emph{raw observation} is the
ROS~2-specific message or event. A \emph{common data record} stores its payload
with source, phase, time, session, and identity information. A
\emph{checker-specific event}, called a DSL record in the prototype, contains
the shape expected by one checking formalism. Monitoring frameworks often use
different event formats, so the boundary between these three forms must be
explicit. A stable recorded format additionally makes it possible to replay a
run or to compare results from different checking tools.

\section{Variability and Feature Models}\label{sec:feature-models}

Systems in the same domain usually share a common core but differ in many
details. Building one configurable infrastructure for such a domain only works
when these common and variable parts are identified first: the common parts
can be implemented once, while the variable parts must become configuration
choices. This requires a systematic way to describe what can vary and which
combinations are allowed.

Feature-Oriented Domain Analysis (FODA) provides such a
description~\cite{kang1990foda}. In FODA, the capabilities of the systems in a
domain are described as \emph{features}, organized in a tree called a
\emph{feature model} or feature diagram. The tree shows which features are
always present, which are optional, and which exclude each other, and it can
be extended with cross-tree constraints between features in different
branches~\cite{benavides2010automated}.
Chapter~\ref{chapter:design} uses this notation to describe the design space
of ROS~2 monitoring solutions, so the notation is introduced here.

Figure~\ref{fig:feature-model-example} shows a small example feature model of
a computer product line. The notation is read as follows:

\begin{itemize}
    \item A \textbf{mandatory} feature (filled circle) is part of every
    product in which its parent appears. Every computer has a processor and
    memory, as well as some storage and ports.

    \item An \textbf{optional} feature (empty circle) may be included or left
    out. A computer may or may not include a dedicated graphics card or a more
    powerful power supply.

    \item An \textbf{alternative} group (empty arc) allows exactly one child
    to be chosen. The processor is from Intel or AMD, but only one processor
    family is selected for a particular model.

    \item An \textbf{or} group (filled arc) allows one or more children to be
    chosen. A computer can include SSD storage, hard disk storage, or both.

    \item A \textbf{cross-tree constraint} (dashed arrow) restricts
    combinations across branches. A dedicated graphics card requires a stronger
    power supply. Constraints can also exclude combinations, for example when
    two features cannot be used together.
\end{itemize}

A concrete product is a selection of features that respects all these rules.
A feature model describes valid design choices; it does not by itself provide
deployment details. Host addresses, ROS names, interface types, class paths,
file locations, and transport parameters belong in a separate deployment
specification.

\section{Deployment and Monitoring Organizations}

The monitoring tasks described earlier in this chapter do not have to run in
one place. Observation, checking, and reporting can be placed at the same
location or spread over several machines. Francalanza et al.\ compare the main
ways in which monitors for decentralized and distributed systems can be
organized~\cite{francalanza2018distributed}. This section summarizes these
monitoring organizations and then fixes the deployment terminology used in the
rest of the thesis.

\subsection{Monitoring Organizations}\label{sec:monitoring-organisations}

Figures~\ref{fig:org-traditional} to~\ref{fig:org-choreographed} show the four
monitoring organizations described by Francalanza et
al.~\cite{francalanza2018distributed}. In the figures, circles are system
processes, hexagons are traces, squares are monitors, and each surrounding
rectangle is a location, such as a machine or a robot. Dotted arrows show
processes contributing events to a trace, dash-dotted arrows show monitors
reading a trace, and solid arrows show interaction between components.

In a \emph{traditional} (centralized) monitoring setup
(Figure~\ref{fig:org-traditional}), all processes run at a single location.
They produce one local trace, and a single monitor at the same location
analyses it. Because everything runs under one clock, the trace is a total
order of the events that actually happened. This is the simplest organization,
but the whole monitoring task rests on one monolithic monitor at one
location~\cite{francalanza2018distributed}.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.58\textwidth]{diagrams/Deployment_Traditional.png}
\caption{Traditional (centralized) monitoring: the processes at one location
produce a single trace that one monitor analyses (adapted
from~\cite{francalanza2018distributed}).}
\label{fig:org-traditional}
\end{figure}

In a \emph{decentralized} monitoring setup
(Figure~\ref{fig:org-decentralized}), the events are still governed by a
single global clock and form one synchronized, totally ordered trace, but the
monitoring work is decomposed into several monitors. The monitors can interact
to combine their partial results, and processes and monitors may be placed at
different locations that share the global clock. This decomposition reflects
that a global property can often be split into smaller properties that
cooperating monitors check independently~\cite{francalanza2018distributed}.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.62\textwidth]{diagrams/Deployment_Centralised.png}
\caption{Decentralized monitoring: several monitors, possibly at different
locations that share a global clock, process a synchronized trace and can
interact with each other (adapted from~\cite{francalanza2018distributed}).}
\label{fig:org-decentralized}
\end{figure}

The remaining two organizations target truly distributed settings, where
processes run at several locations without a global clock. Each location then
produces its own local trace, and the events of different traces can only be
partially ordered. In an \emph{orchestrated} monitoring setup
(Figure~\ref{fig:org-orchestrated}), the analysis is still performed centrally:
the monitors run at a remote location and access the trace events produced at
the other locations. Centralising the analysis keeps the monitor logic simple,
but the trace data has to be transmitted remotely. This increases the
communication overhead as the system grows, and it can expose private trace
data on the network and make the central monitor a single point of
attack~\cite{francalanza2018distributed}.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.66\textwidth]{diagrams/Deployment_Orchestrated.png}
\caption{Orchestrated monitoring: traces are produced locally at the observed
locations, while remote monitors at a central location perform the analysis
(adapted from~\cite{francalanza2018distributed}).}
\label{fig:org-orchestrated}
\end{figure}

In a \emph{choreographed} monitoring setup
(Figure~\ref{fig:org-choreographed}), the verification work is instead pushed
to the locations where the traces are produced. Local monitors analyse local
traces and, when they contribute to the same global property, coordinate with
each other. This reduces data exposure and communication overhead, but it is
more complex to set up: the properties have to be decomposed into coordinated
local monitors, and the monitored locations must allow the extra local
computation~\cite{francalanza2018distributed}.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.66\textwidth]{diagrams/Deployment_Choreographed.png}
\caption{Choreographed monitoring: monitors run at the locations where the
traces are produced and coordinate with each other when needed (adapted
from~\cite{francalanza2018distributed}).}
\label{fig:org-choreographed}
\end{figure}

These organizations frame the deployment choices for a ROS~2 monitoring
infrastructure. A single robot with an on-board monitor is a traditional
setup. As soon as observations are checked on another machine, or several
robots are observed together, the infrastructure moves towards an orchestrated
or choreographed organization, and the partial ordering, communication, and
data exposure trade-offs above apply.
Section~\ref{sec:deployment-views} relates the deployment forms supported by
this thesis to these organizations.

\subsection{Deployment Terminology}\label{sec:deployment-terminology}

The thesis uses the following deployment terms:

\begin{description}
  \item[Host.] A physical or virtual machine on which one or more executable
  runtimes run.

  \item[Runtime.] One executable monitor or verifier process built from a YAML
  configuration.

  \item[Integrated deployment.] Collection, processing, checking, and result
  export run in one ROS~2-facing runtime. This corresponds to the traditional
  organization above.

  \item[Split deployment.] A ROS~2-facing monitor runtime collects records and a
  separate verifier runtime checks them. They may run on one host or on
  different hosts. With a remote verifier, this corresponds to an orchestrated
  organization with one central analysis location.
\end{description}

These two deployment forms are representative endpoints, not an exhaustive
catalogue. The reference architecture also permits several monitor or verifier
runtimes and different placements, provided that their links are configured.

\section{Transport}

When monitoring components run in different processes or on different
machines, as in the orchestrated and choreographed organizations above, they
need a transport mechanism to exchange data. Many protocols can fill this
runtime: the components could communicate through the DDS middleware that ROS~2
itself uses~\cite{macenski2022ros2,omgdds2015}, through plain TCP or UDP
sockets~\cite{rfc9293,rfc768}, through web protocols such as HTTP or
WebSocket~\cite{rfc9110,rfc6455}, or through message brokers using protocols
such as AMQP~\cite{amqp10}, Kafka~\cite{kreps2011kafka}, or
MQTT~\cite{mqtt5spec}. These options differ in how they
handle addressing, delivery guarantees, and decoupling between sender and
receiver. Monitoring records can also simply be written to files and read by
another process. The reference architecture treats this carrier as
replaceable.

The prototype uses MQTT in its split online deployment. MQTT is a small,
standard publish--subscribe protocol that is commonly used in robotics and
Internet-of-Things systems; MQTT~5.0 is an OASIS standard~\cite{mqtt5spec}.
Publishers send messages to named topics through a broker, and subscribers
receive messages from the topics they select. Because the broker decouples
publishers from subscribers, neither side needs to know the network address of
the other. In the split deployment of this thesis, the robot-side monitor
publishes serialized records to a configured MQTT topic prefix, and a verifier
subscribes to that topic filter and receives the data without a ROS~2
installation or a direct connection to the robot process.

MQTT also gives a configurable delivery trade-off through its own QoS levels.
QoS~0 sends a message at most once and is useful when occasional loss is
acceptable. QoS~1 retries until the broker acknowledges the message, which can
duplicate messages and therefore requires identifiers to make duplicates
recognizable. QoS~2 provides an exactly-once handshake at the cost of additional
protocol traffic. The infrastructure keeps the session and
record identifier inside each observation, so the transport does not have to
carry the semantic identity of an observation. MQTT is an implementation
choice for the prototype, not a mandatory dependency of the reference
architecture.
