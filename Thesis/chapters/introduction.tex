\chapter{Introduction}\label{chapter:introduction}

\section{Context and Motivation}

Robots often work in changing environments. Their behaviour depends on
software, hardware, sensor data, communication, and the physical world. Some
events can only be seen while the robot is running. For this reason, testing a
robot before deployment is important, but it is not always enough. Developers
also need to observe the robot during operation.

Many modern robots are built with the Robot Operating System~2 (ROS~2). It is a middleware 
and software platform that runs on top of a conventional operating system (usually Ubuntu) and
provides communication, discovery, build tools, and reusable packages for
robotic software~\cite{macenski2022ros2}. A ROS~2 application is composed of
\emph{nodes}: programs with a focused task, such as reading a sensor or
planning a route. Nodes communicate through typed interfaces. \emph{Topics}
are mainly used for continuous data streams, \emph{services} for
request-response interactions, and \emph{actions} for long-running tasks that
provide feedback while they run~\cite{macenski2022ros2,ros2interfaces}.
Chapter~\ref{chapter:background} explains these mechanisms in detail.

A common way to observe a system during operation is \emph{runtime
monitoring}. Runtime monitoring collects information from a running system.
The collected information can be used to find errors, understand runtime
behaviour, or check whether the system follows expected
rules~\cite{rabiser2019domain,leucker2009brief}. The component that performs
this task is called a \emph{monitor}: it observes the running system, records
what it sees as observations, and can analyse these observations, for example
by checking them against an expected property and reporting a verdict. Unlike
model checking, runtime monitoring does not study every possible system state.
It studies the behaviour that actually happens during an execution. When the
emphasis is on checking the observed behaviour against a specification, the
technique is also called runtime verification~\cite{leucker2009brief}.

Runtime monitoring is particularly relevant for ROS~2 applications. The
modular node structure makes it easier to reuse and replace software parts,
but it also spreads the behaviour of the robot across many nodes and
interfaces. Important information may come from several topics, services, or
actions. It can therefore be difficult to understand what the full system is
doing by looking at any single component.

ROS~2 already provides several ways to observe a system. For example, a
monitor can subscribe to a topic, read service introspection events, or
observe the hidden topics used by actions. Lower-level tools can also trace
ROS~2 execution. The difficult part is turning these possibilities into a
reusable monitoring setup: developers still need to decide what to observe,
how much data to keep, where to send the data, and how to check it. These
decisions are often implemented again for every application. This thesis
presents a configurable monitoring infrastructure that turns these separate
observation possibilities into a reusable monitoring foundation for ROS~2
applications.

\section{Problem Statement}

ROS~2 applications need runtime monitoring. A robotic application interacts
with an environment that testing cannot fully cover: failures caused by
timing, sensor noise, hardware behaviour, or unexpected environment states
often appear only while the system is running. In addition, because a ROS~2
application is distributed over many nodes, no single component has a complete
view of the system behaviour. Runtime monitoring is therefore needed to detect
errors, to understand what the system is doing, and to check whether the
running system still satisfies its requirements.

Setting up monitoring for a concrete application, however, involves many
configuration options and scenarios. The developer has to decide \emph{what}
to observe: which topics, services, and actions carry the relevant behaviour.
They have to decide \emph{how} to observe it: through extra subscriptions,
service introspection, lower-level tracing, or instrumented application code.
They have to decide how much data to keep: complete messages support offline
replay, while a few fields from a high-rate stream may be all that a check
needs. They have to decide how the properties of interest are specified and
checked: as simple thresholds, state machines, temporal-logic formulas, or
project-specific checking services. Finally, they have to decide how the
monitor is deployed: together with the application, close to the robot, or on
a separate machine that receives the observations over a network.

All of these choices have advantages and disadvantages, and they interact with
each other. For example, observing everything makes checking flexible but can
overload storage and transport, while a remote verifier eases the load on the
robot but adds a network boundary. Because the choices interact, an ad-hoc
combination assembled for one application rarely carries over to the next one.
There is a need for a systematic way to specify a monitoring solution: a
description of the available options and a means to select among them.

The second problem is that implementing a chosen monitoring solution is time
consuming. Much of the required code, such as subscribing to interfaces,
decoding typed messages, attaching timestamps and context, serializing data,
and transporting it to checkers and files, is essentially the same in every
project, yet it is written again for each application. This repeated
implementation effort should be reduced by automation and by reusable,
configurable infrastructure support.

These two problems, the systematic specification of a monitoring solution and
the reusable implementation of it, are the subject of this thesis. The thesis
is not concerned with how properties are specified or how they are checked.
Existing specification languages and checking tools can be attached to the
infrastructure through defined interfaces; the infrastructure delivers the
observations they need.

\section{Research Objective and Questions}

The objective of this thesis is to design, implement, and evaluate a
configurable monitoring infrastructure for ROS~2 applications. The
infrastructure should collect different ROS~2 observations in a common way. It
should also allow users to select the observation, processing, checking,
output, and deployment setup through configuration rather than through new
monitoring code.

The following research questions guide the work:

\begin{description}
    \item[RQ1] What monitoring capabilities currently exist for ROS~2, and
    which observation gaps remain?

    \item[RQ2] What are the main commonalities and variabilities among
    existing monitoring architectures for ROS~2 applications?

    \item[RQ3] What does a generic reference architecture for ROS~2
    monitoring look like, and can it incorporate the features identified in
    RQ2?

    \item[RQ4] To what extent does the implemented infrastructure support the
    monitoring needs of realistic ROS~2 applications?
\end{description}

\section{Approach}

Each research question is answered as follows.

To answer RQ1, we review existing research and tools for monitoring ROS and
ROS~2 applications. We group the approaches by the level at which they observe
the system: ROS graph instrumentation, network-level observation, and
lower-level tracing. The review identifies which ROS~2 elements each approach
can observe and which observation gaps remain
(Chapters~\ref{chapter:background} and~\ref{chapter:related_work}).

To answer RQ2, we perform a domain analysis of the reviewed monitoring
approaches. We identify the tasks they share, such as collecting, processing,
routing, checking, and reporting, and the points where they differ, such as
the observable elements, the monitoring architecture, the monitoring mode, the
system configuration, and the implementation technique. We capture these
commonalities and variabilities in a feature model
(Chapter~\ref{chapter:design}).

To answer RQ3, we design a reference architecture for ROS~2 monitoring and
implement it in a Python prototype (Chapters~\ref{chapter:design}
and~\ref{chapter:implementation}). The architecture is a configurable
pipeline. A collector observes a configured topic, service event stream, or
action feedback and status stream and stores each observation in a common data
record that carries the payload together with source information, timestamps,
a session identifier, and a record identifier. Optional transformers reduce or
reshape records, dispatchers route them to outputs and checking components,
converters prepare them for property-specific verdict services, and exporters
deliver data and verdicts to files, standard output, or MQTT. The same
pipeline supports an integrated deployment, in which all steps run in one
ROS~2-facing process, and a split deployment, in which a robot-side monitor
sends records over MQTT to a separate verifier without a ROS~2 dependency. We
then check the architecture against the feature model from RQ2 to determine
which of the identified features it can incorporate.

To answer RQ4, we evaluate the prototype through case studies that cover the
three ROS~2 communication mechanisms and both deployment forms, including a
Navigation~2 (Nav2) case study; Nav2 is chosen because it combines topics,
services, and actions in a realistic robotic application. The case studies are
complemented by unit tests, Docker Compose deployment examples, offline
replay, and a multi-robot scenario (Chapter~\ref{chapter:evaluation}).

\section{Contributions}

The contributions of this thesis are:

\begin{enumerate}
    \item An overview of existing ROS~2 monitoring approaches, the observation
    mechanisms they use, and the gaps that remain (RQ1).

    \item A feature model that captures the commonalities and variabilities of
    ROS~2 monitoring solutions (RQ2).

    \item A reference architecture for ROS~2 monitoring, organized as a
    pipeline that separates data collection, processing, transport, checking,
    and output, together with a prototype that implements it (RQ3).

    \item A common data format for representing observations of topics,
    services, and actions. Each observation is stored as a record that
    combines the observed payload with its source, timestamps, and session
    identity, so that later processing and checking steps can treat the three
    kinds of observations in the same way (RQ3).

    \item A configuration mechanism with extension points. Users select data
    sources, processing steps, checks, outputs, and the deployment form in
    YAML configuration files. The deployment form can be integrated, where
    collection and checking run in one process, or split, where a robot-side
    collector sends records to a remote verifier. Project-specific converters,
    checkers, and exporters can be added as separately developed components
    without changing the infrastructure code (RQ3).

    \item An evaluation of the infrastructure through three case studies
    (RQ4). A speed-limit case study demonstrates topic monitoring: velocity
    messages are collected, reduced to the relevant fields, and checked
    against a threshold in both the integrated and the split deployment. A
    service reset case study demonstrates service monitoring: reset requests
    and responses are captured through service introspection and checked for
    their effect on the robot state. A Navigation~2 case study demonstrates
    action monitoring in a realistic application: navigation goals are
    followed through action feedback and status, together with the topics that
    Nav2 uses during navigation.
\end{enumerate}

The main contribution is the reusable monitoring infrastructure. It is not a
new checking algorithm. Different checking tools can be connected to the
infrastructure through its extension interfaces.
