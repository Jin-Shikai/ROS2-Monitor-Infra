\chapter{Evaluation}\label{chapter:evaluation}

This chapter evaluates the implemented infrastructure and answers RQ4:

\begin{quote}
\textbf{RQ4:} To what extent does the implemented infrastructure support the
monitoring needs of realistic ROS~2 applications?
\end{quote}

The evaluation uses five experiments. E1 starts with one topic and an
integrated monitor. E2 adds services, actions, and a split deployment over
MQTT. E3 applies the infrastructure to an unmodified Nav2 application. E4
extends the same setup to two robots and a property that uses observations
from both robots. E5 places the robots, monitor, and verifier on three
different physical machines. Together, the experiments cover the main
capabilities introduced in Chapters~\ref{chapter:design}
and~\ref{chapter:implementation} and provide complementary evidence for RQ4.

\section{Evaluation Method}
\label{sec:eval-method}

E1--E4 ran on the same Ubuntu~24.04 workstation with ROS~2 Kilted. The robot
experiments used Gazebo and Nav2. These MQTT experiments used a local
Mosquitto broker on port~1884. E5 used the same workstation for Gazebo and
Nav2, an Ubuntu~24.04 Raspberry Pi for collection and the broker, and a macOS
laptop for verification. Gazebo and RViz were used to inspect the robot
experiments, they make the
route changes, robot crossings, and physical three-machine setup visible;
the tables are calculated from the recorded experiment artifacts.

The terms \emph{integrated} and \emph{split} describe process placement. 
E1 checks properties inside the monitor
process. In E2--E4, the monitor and the verifier are separate
processes, but they still run on the same machine and exchange records
through an MQTT broker on \texttt{localhost}. This setup checks whether the
two runtime roles can be separated without changing the verdicts. 
E5 uses the same split but
places the ROS~2 application, monitor, and verifier on three computers. DDS
carries the robot topics from the workstation to the Pi, and MQTT carries the
resulting data records from the Pi to the laptop, 
the verification was done on a the laptop without ROS~2 installed.

The reported detection latency is the time between collection of the record that determines a
result and export of the verdict. Record counts and sequence numbers
are used to check that unfiltered observations are not lost. CPU and memory use
are sampled during each run. These measurements describe the prototype on the evaluation
hardware.

\paragraph{Deployment.} One physical workstation runs two ROS~2 processes: a 
node and the monitor. The collector, converter, and verdict service
all run inside the monitor process. No MQTT broker or separate verifier is used.

\section{E2: Topics, Services, and Actions in a Split Deployment}
\label{sec:eval-e2}

E2 separates collection from checking while adding service and action
observations.

\paragraph{Deployment.} All components still run on one physical workstation,
but in separate processes. Three ROS~2 stimulus processes
publish the test data. A monitor process collects their observations through
DDS. It writes the records locally and sends them to a Mosquitto process. A
separate verifier process receives the records from MQTT on
\texttt{localhost}. The speed rule runs both inside the monitor and inside the
verifier; the reset rule runs in the verifier.

\paragraph{Sources and expected observations.}
Table~\ref{tab:eval-e2-sources} lists all four monitored sources.

\paragraph{Rules.} The monitor and verifier check the following speed rule:

\[
    \texttt{linear.x} \leq 0.5\ \text{m/s}.
\]

The verifier also checks the following reset rule:

\[
    \text{distance to origin after a successful reset}
    \leq 0.05\ \text{m within 1 second}.
\]

The speed rule is checked twice from the same records, so the local and remote
verdict streams should be identical. The reset rule uses a service-response
record and a later odometry record. The Fibonacci action has no separate rule;
its expected feedback and final status are used to check action collection.

\paragraph{Results.}
In the 120-second reference run, the monitor collected 1458 records from the
four sources. The local and remote speed checks each produced 40 verdicts,
with the same result and contributing record identifiers in every case. The
reset rule produced 39 alternating positive and negative verdicts, as expected
from the test node. The action collector recorded all feedback and final
statuses for 23 goals.

\section{E3: Monitoring a Nav2 Application}
\label{sec:eval-e3}

E3 replaces the small test nodes with an unmodified Nav2 application. A
TurtleBot3 moves between the left and right sides of a corridor map in Gazebo.
The purpose is to check whether the infrastructure can follow real Nav2 topic
and action data while the available route and action outcome change.

\paragraph{Deployment.} One physical workstation runs Gazebo, Nav2, the
mission process, the monitor, Mosquitto, and the verifier. Nav2 and the monitor
are separate ROS~2 processes connected through DDS. The monitor and verifier
are also separate processes and exchange records through MQTT on
\texttt{localhost}. The deployment is therefore split at the process level, 
on the same machine.

\paragraph{Sources and expected observations.}

\paragraph{Rules.} The verifier checks the following speed rule:

\[
    \texttt{linear.x} \leq 0.2\ \text{m/s}.
\]

It also checks the following navigation rule:

\[
    \text{goal status} = \textsc{succeeded}
    \quad\text{and}\quad
    \text{duration} \leq 35\ \text{s}.
\]

A goal receives a negative verdict if it exceeds the time limit, is
cancelled, or ends with an aborted status. Odometry is reduced to the required
fields and limited to 5~Hz before it is stored and sent to the verifier.

first remains in place. No route then connects the two sides of the map.

outcome and duration. Mean speed-verdict latency was 0.58~ms.

\paragraph{Finding.} E3 shows that the infrastructure can monitor a realistic
ROS~2 application without changes to Nav2. The three goals exercise the
complete navigation rule: success before the deadline, a goal still running
at the deadline, and an explicit Nav2 failure. In each case the online verdict
agreed with the route and action logs recorded independently.

\section{E4: Monitoring Two Nav2 Robots}
\label{sec:eval-e4}

E4 uses two namespaced TurtleBot3 and Nav2 instances. The robots start on
opposite sides of the map, move past each other, and then return. The purpose
is to check that observations remain associated with the correct robot and
that one rule can combine positions from both namespaces.

\paragraph{Deployment.} All components again run on one physical workstation.
Gazebo simulates both robots, and two namespaced Nav2 stacks run as separate
ROS~2 components. One monitor collects both namespaces through DDS. The
monitor sends records through a local Mosquitto process to one verifier
process. The verifier contains two independent speed checks and one check that
uses positions from both robots. As in E2 and E3, MQTT separates processes but
does not cross a physical network.
Figure~\ref{fig:eval-e4-deployment} summarizes this placement and the two
communication steps.

\paragraph{Rules.} The verifier checks the following speed rule separately for
each robot:

\[

\]

\[
    \text{distance between the two robots} \geq 1.0\ \text{m}.
\]

expressed in the shared map frame. Each new pose is paired with the latest pose
of the other robot. A negative verdict is produced when the distance first
falls below 1.0~m, and a positive verdict is produced when it rises above the
limit again. Gazebo positions are recorded separately so that this result can
also be compared with the simulated physical distance.

navigates to the other side and then returns to its starting side, producing
two crossings and four completed navigation goals.

\section{E5: Distributed Deployment on Three Machines}
\label{sec:eval-e5}

E5 repeats the E4 mission and rules, but changes where the runtime roles run.
The purpose is to check whether the same monitoring setup continues to work
when DDS and MQTT cross physical-machine boundaries and the verifier has no
ROS~2 installation.

\paragraph{Deployment.} The Ubuntu workstation runs Gazebo, two Nav2 stacks,
and the mission. A Raspberry Pi running Ubuntu receives the six E4 topics over
DDS, collects them as data records, and publishes them to a Mosquitto broker
on the same Pi. A macOS laptop receives these records over MQTT and runs the
three E4 checks using Homebrew Python. The Pi and workstation use ROS~2
Kilted and the default Fast DDS implementation. The laptop runs no ROS~2
software.

The Pi also runs a second verifier as an experimental reference. The Pi and
Mac verifiers subscribe to the same MQTT topic and use the same generated
checking configuration. Comparing their verdict files therefore tests whether moving
the verifier to the Mac changes the property result or its contributing
record identifiers. This reference process is not required by the deployment
itself.

\paragraph{Measurements.} Nav2 message headers use simulation time, so they
cannot be compared with a wall-clock collection timestamp. An additional
5~Hz pose message therefore carries the workstation wall clock in its header.
It is collected on the Pi but does not feed a rule. This provides a separate
measurement of the workstation-to-Pi DDS path.

The workstation compares its clock with the Pi and Mac clocks at the start
and end of the run. The measured offsets are subtracted from the DDS and
remote-verdict latencies. For the reported run, mean Mac-minus-Pi offset was
$+1.369$~ms. The offset changed during the run, and the network exchange used
to estimate it also has finite delay. The combined uncertainty bound was
1.926~ms. The corrected cross-machine latency values should therefore be read
at millisecond precision.

\paragraph{Results.} All four navigation goals succeeded. In the first leg,
robot~2 and robot~1 finished in 24.6 and 35.9 seconds. In the second leg,
robot~1 and robot~2 finished in 28.1 and 30.5 seconds. The Pi collected 3667
records from the E4 sources and 506 measurement-probe records. Both verifiers
received all 4173 data records. The Mac subscribed after the initial session
bookend had been sent, but received every data record and the final bookend.

The two speed streams contained 12 and 18 transitions. Every Mac verdict
matched replay of the corresponding Pi command stream. The separation stream
contained two violation periods and two recoveries. All four transitions
matched replay, including both contributing pose-record identifiers. They
also matched the two physical periods below 1.0~m in the Gazebo position log.
The minimum localized and physical separations were $0.547$~m and $0.621$~m.
All four final physical positions were within $0.10$~m of the requested goal.

The serialized fleet records contained 18.245~Mbit over 105.1 seconds, or

\paragraph{Finding.} E5 shows that the collector and verifier can run on
different operating systems and processor architectures while preserving the
same verdict stream. Direct DDS discovery between the workstation and Pi
remained available for the full mission, and MQTT delivered every data record
to the Mac. The observed violations and recoveries on the Mac, together with
the identical Pi reference stream, show that physical distribution did not
change the meaning of the E4 checks.

The results answer RQ4 positively within the scope of the prototype. The
infrastructure supports the application-level monitoring needs exercised by
these case studies: topic, service, and action observations; processing before
transport; checking in the monitor or in a separate verifier; correlation of
several observations; and separation of data from multiple robots. The Nav2
experiments show that these capabilities apply to an existing ROS~2
application without modifying its navigation code. The generated
configurations show that deployment and checking components can be
changed through configuration rather than changes to the monitoring core.
E5 additionally shows that the ROS~2-facing part can run on a Pi while the
checking part runs on a macOS machine without ROS~2.

The evaluated scope is one local network, up to two simulated robots, and the
topic, service, and action observations selected in
Chapter~\ref{chapter:design}. Within that scope, E1--E5 provide consistent
evidence that the implemented infrastructure supports the monitoring needs
stated in RQ4, from local topic checks to a three-machine Nav2 deployment.
