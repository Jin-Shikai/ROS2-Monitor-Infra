\chapter{Implementation}\label{chapter:implementation}

\section{Implementation Overview}

The prototype is implemented in Python for ROS~2 Kilted. Before individual
classes are discussed, Figure~\ref{fig:implementation-chain} shows the complete
transformation chain with its concrete artifacts. A deployment specification
and user plug-ins are inputs to configuration generation. The generated YAML
starts either a \texttt{monitor\_node} runtime, which has ROS~2 access, or a
\texttt{node\_runner} verifier runtime, which can run without ROS~2.

\begin{figure}[htbp]
  \centering
  \resizebox{\textwidth}{!}{\input{figures/implementation_chain}}
  \caption{Implementation view of the chain in
  Figure~\ref{fig:configuration-workflow}: authored specifications and
  plug-ins, the generator, the generated runtime configurations, and the two
  executable entry points.}
  \label{fig:implementation-chain}
\end{figure}

A \emph{runtime} in this chapter means one executable process built from one
runtime YAML file. It owns its configured sources, processing and checking
graph, outputs, and lifecycle. A host can run more than one runtime, although
the generator normally emits one consolidated configuration for each host role.

\section{Technology Choices}

ROS~2 provides the Python client library \texttt{rclpy}, which allows the
monitor to join the ROS graph as a normal node. Python also has runtime type
utilities through \texttt{rosidl\_runtime\_py}. These utilities resolve ROS~2
message, service, and action classes from their type names, so a configured
source can be collected without generating source-specific monitoring code.
Python also makes project-specific converters and verdict services easy to
add.

Only the collector layer imports ROS~2 packages. The remaining modules use the
Python standard library, \texttt{PyYAML} for configuration parsing, and
\texttt{paho-mqtt} for MQTT transport. As a result, the verifier side of a
split deployment can run on a plain Python installation. If \texttt{paho-mqtt}
is unavailable, MQTT components are skipped at construction time while the rest
of the modules remain importable and testable.

\subsection{Collectors}

The monitor runtime builds one collector for each configured ROS~2 resource:

\begin{description}
  \item[Topic collector.] It resolves the message class at startup, creates a
  normal subscription, recursively converts each message to a dictionary, and
  creates a topic data record.

  \item[Service collector.] It resolves the service event class and subscribes
  to the hidden service-event topic for the configured service
  (Section~\ref{sec:observing-services}). The client or server must enable
  service introspection in \texttt{CONTENTS} mode. Event type distinguishes
  request from response; the client identifier and sequence number are retained
  as metadata.

  \item[Action collector.] It subscribes to the configured action's hidden
  feedback and status topics. The configured phases determine which hidden
  topics are used. Goal, cancellation, and result interactions are
  services and require separate service-event collectors for a complete trace.
\end{description}

All three collectors observe event topics that ROS~2 itself exposes; no
interceptor is placed between application nodes, and the application code is
not modified.

\subsection{Common Records and Serialization}

The \texttt{DataRecord} dataclass implements the schema from
Section~\ref{sec:common-record}. It assigns a session identifier, a per-source
sequence number, and a record identifier formed from the session, source type,
source name, phase, and sequence. It stores monitor wall-clock time and, when
present, the message header timestamp.

Serialization uses one JSON object per line. Empty optional fields are omitted.
Because the payload has already been converted recursively, nested ROS
messages, arrays, sequences, and primitive values remain valid JSON data. The
same JSON is used for files and MQTT, so split deployment does not change the
meaning of the record.

\subsection{Transformers and Dispatchers}

Each collector owns an ordered transformer pipeline. The built-in
\texttt{FieldExtractor} selects nested fields, \texttt{RateThrottler} limits the
maximum output frequency, and \texttt{OnChangeFilter} suppresses repeated
values. A transformer can return no record to stop processing. Names of
successful transformations are appended to record metadata.

A dispatcher fans one record out to any number of exporters and checking
chains. If one exporter fails, the dispatcher reports the failure and
continues with the remaining exporters. The same dispatcher implementation is
used for data records, converter output, and verdicts.

\subsection{Checking Graph}

A \emph{checking graph} is the configured directed graph from common records to
converters, verdict services, and outputs. It is not a ROS graph. A converter
selects one or several source records and emits a checker-specific DSL record.
A verdict service evaluates that record and may emit a verdict. Links can also
chain a derived record into another converter.

The following compact YAML fragment represents one graph:

\begin{lstlisting}[language={},caption={Runtime YAML for a speed property.},
label={lst:speed-yaml}]
topics:
  - name: /cmd_vel
    type: geometry_msgs/msg/Twist

converters:
  - id: speed_input
    type: custom.speed:SpeedConverter
    inputs: [/cmd_vel]

verdict_services:
  - id: speed_limit
    type: custom.threshold:ThresholdVerdict
    threshold: 0.5

links:
  - {from: "converter:speed_input", to: "verdict:speed_limit"}
\end{lstlisting}

The runtime builder validates component identifiers, loads the selected classes,
constructs dispatchers, and starts scheduled converter work only after wiring
is complete. Session-start and session-end records are retained as evidence but
are not passed to property checking.

\section{Exporters, Sources, and Transports}\label{sec:impl-transport}

An exporter is a sink for records. It accepts a record and can later be flushed
or closed. The prototype includes file and MQTT data exporters. The file
exporter appends JSONL records to a per-session file and flushes at a
configurable interval. The MQTT exporter publishes data records to topics
derived from the source:
\texttt{<prefix><source\_type>/<source\_name>}. Session records are published
on a separate \texttt{<prefix>\_session} topic. The connection is established
asynchronously, reconnects automatically, and uses a bounded outbound queue so
that a slow broker does not block ROS~2 callback threads.

A source is the verifier-side counterpart of an exporter. It reads records
from a transport and injects them into a dispatcher. The MQTT source subscribes
to a topic filter and parses each payload into a data record. The file source
replays a JSONL file. With the \texttt{follow} option, it keeps reading new
lines appended to the file; without it, the source replays the file once,
optionally with a delay between records.

Converter output can also cross a transport boundary. The same file and MQTT
carriers are implemented for converter output, and verdicts have file,
standard-output, and MQTT exporters. Because each boundary is represented by
an exporter on one side and a source on the other, a pipeline stage can run
in-process or across a transport without changing the stage implementation.

\section{Plug-ins and DSL Adaptation}\label{sec:plugins}

A converter plug-in subclasses \texttt{DataConverter} and implements
\texttt{convert(record)}. It may return no value, a dictionary, or a derived
record. Stateful converters can correlate sources, retain windows, or schedule
deadline events. A verdict-service plug-in subclasses
\texttt{VerdictService} and implements \texttt{evaluate(dsl\_record)}. Its
result uses the common \texttt{Verdict} structure:
\texttt{property\_id}, Boolean result, timestamp, details, session identifiers,
and contributing record identifiers.

The plug-in class is selected by an import path such as
\texttt{custom.speed:SpeedConverter}. The loader imports it, verifies that it
implements the required base class, and passes configured keyword arguments to
its constructor. Thus ``supporting a DSL'' has a concrete meaning:

\begin{enumerate}
  \item define the DSL-record fields expected by the checker;
  \item implement a converter that produces those fields and retains input
  record identifiers;
  \item implement or wrap a verdict service that evaluates the property; and
  \item select both classes and their parameters in the deployment
  specification.
\end{enumerate}

The concrete plug-ins used in the case studies live in the \texttt{custom/}
package and illustrate different plug-in patterns:

\begin{itemize}
    \item \texttt{CmdVelSpeedConverter} maps a velocity record to the single
    field checked by a threshold property. It is the smallest stateless
    converter pattern.

    \item \texttt{ThresholdVerdict} compares one field with a bound. It emits a
    violation verdict when the violation starts and a recovery verdict when
    the value returns inside the bound, so only satisfaction changes are
    reported.

    \item \texttt{ResetPoseEffectConverter} and its verdict service check a
    property over two interfaces: after a successful \texttt{/reset\_pose}
    service response, the odometry must return close to the origin within a
    deadline. The converter correlates service records with odometry records
    and uses a timer to report a violation when the deadline expires.

    \item \texttt{RelativeSpeedConverter} joins streams from two robots and
    derives a joint value, demonstrating a stateful converter over more than
    one data source.
\end{itemize}

Converters and verdict services do not import ROS~2 packages and do not assume
a particular property language. A temporal-logic engine could be wrapped
behind the same interfaces; the prototype ships the small adapters above
rather than integrations with every formalism named in the feature model.

\section{The Verifier Runtime}\label{sec:impl-node-runner}

The verifier-side entry point is \texttt{node\_runner.py}. It runs the same
checking graph without a ROS~2 dependency. Its configuration uses
\texttt{inputs} in place of collector sections. An input receives data records
or converter output from MQTT or a file and feeds them into the graph.

A single runner process can host converters, verdict services, or both. It can
therefore act as a complete verifier, one half of a separated checking chain,
or a relay that filters records and republishes them. The runtime role is
determined by the YAML file.

The integrated deployment runs the full pipeline in one monitor process. The
split deployment runs the monitor process near the robot and sends serialized
records to one or more verifier runtimes. Since both deployments exchange the
same data record format, a recorded JSONL file can later be replayed through
the same checking graph for offline analysis.

\section{Deployment Specification and Configuration Generation}
\label{sec:impl-config-gen}

A multi-host deployment needs several YAML files that agree on transports,
topic names, and payload kinds. Writing these files by hand is error-prone. The prototype therefore includes a configuration generator that derives
the runtime YAML files from one deployment specification. The JSON deployment
specification contains:

\begin{description}
  \item[\texttt{hosts}] named deployment hosts;
  \item[\texttt{runtimes}] ROS~2 sources, monitor roles, converters, and
  verdict-service roles placed on each host; and
  \item[\texttt{links}] source and destination runtimes, payload type
  (\texttt{records} or \texttt{dsl}), and file or MQTT transport settings.
\end{description}

The specification model is intentionally close to the runtime concepts, as
shown in Figure~\ref{fig:config-generation-model}. A \texttt{Host} is a
placement boundary. A \texttt{Runtime} is one executable role placed on a
host. A \texttt{Source} is a topic, service, or action declared by a
\texttt{ros2} runtime. A \texttt{Link} connects two runtimes and contains a
\texttt{Transport}; existing transport kinds are \texttt{mqtt} and
\texttt{file}.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{diagrams/CodeGen.png}
    \caption{Data model of the deployment specification. Hosts contain
    runtimes, \texttt{ros2} runtimes declare monitorable sources, and links
    define the transport used between runtimes. The root element, labelled
    \emph{GenerationRequest} in the diagram, is the deployment specification.}
    \label{fig:config-generation-model}
\end{figure}

For each host, the generator chooses a ROS~2-facing monitor configuration or a
ROS-independent verifier configuration. These start \texttt{monitor\_node} and
\texttt{node\_runner}, respectively. Same-host
links become in-process graph links. Cross-host record links create a matching
data exporter and transport source; cross-host DSL links create matching output
and input endpoints. Both sides derive the same MQTT topic or shared file path.

Algorithm~\ref{alg:config-generation} shows the generation procedure. It
first builds an index of sources, runtimes, host placement, and cross-host
links. It then emits at most one YAML file per host: a monitor configuration
for a host with a monitor runtime, or a runner configuration for a host that
only runs checking components.

\begin{algorithm}[htbp]
\caption{Generate runtime YAML configurations from a deployment specification}
\label{alg:config-generation}
\begin{algorithmic}[1]
\Require deployment specification $D$
\Ensure generated configurations $F$
\State $F \gets \emptyset$
\State $I \gets \Call{BuildIndex}{D.\text{hosts}, D.\text{links}}$
\ForAll{host $H$ in $D.\text{hosts}$}
  \State $K \gets$ the set of runtime kinds on $H$
  \If{\texttt{monitor} is in $K$}
    \State $Y \gets \Call{NewMonitorConfig}{H}$
    \ForAll{monitor runtime $M$ on $H$}
      \State $E \gets \Call{RecordExporters}{M,I}$
      \ForAll{source id $s$ in $M.\text{subscribe}$}
        \State add $\Call{SourceEntry}{I.\text{sources}[s],E}$ to $Y$
      \EndFor
    \EndFor
    \State $G \gets \Call{NewGraphSection}{H,I}$
    \ForAll{converter runtime $C$ on $H$}
      \State reject unsupported cross-host record inputs to $C$
      \State $\Call{AddConverter}{G,C}$
    \EndFor
    \ForAll{verdict-service runtime $V$ on $H$}
      \State reject unsupported cross-host DSL inputs to $V$
      \State $\Call{AddVerdict}{G,V}$
    \EndFor
    \State $\Call{ApplyGraph}{G,Y}$
    \State $F[H.\text{id}] \gets Y$
  \ElsIf{$K$ contains \texttt{converter} or \texttt{verdict\_service}}
    \State $Y \gets \Call{NewRunnerConfig}{H}$
    \State $G \gets \Call{NewGraphSection}{H,I}$
    \ForAll{converter runtime $C$ on $H$}
      \State add incoming cross-host record inputs for $C$
      \State $\Call{AddConverter}{G,C}$
    \EndFor
    \ForAll{verdict-service runtime $V$ on $H$}
      \State add incoming cross-host DSL inputs for $V$
      \State $\Call{AddVerdict}{G,V}$
    \EndFor
    \State $\Call{ApplyGraph}{G,Y}$
    \State $F[H.\text{id}] \gets Y$
  \EndIf
\EndFor
\State \Return $F$
\end{algorithmic}
\end{algorithm}

specification and the generated-file interpretation.

\section{Operational Support}

Runtime YAML can be checked before startup, and the implementation logs the
resolved graph. File outputs support offline replay through
\texttt{FileReplaySource}; MQTT outputs use selectable broker, port, topic, and
QoS settings. The repository provides a container definition for repeatable
packaging, but the heterogeneous experiment also runs a standalone verifier in
a normal Python environment to demonstrate separation from ROS~2.

\section{Chapter Summary}

The implementation turns one deployment specification and optional
property-specific plug-ins into executable runtime configurations. Reusable
collectors expose topics, service events, and action feedback/status as common
records. Transformers, dispatchers, file/MQTT transport, and evidence handling
are reused, while converters and verdict services isolate DSL and property
logic. The next chapter evaluates this data path and the implementation work
the infrastructure saves.
